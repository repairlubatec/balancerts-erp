# Notas de auditoria em curso

## Evidências iniciais

A navegação expõe 14 áreas: Minhas Empresas, Empresas, Contabilidade, Tesouraria, Facturação, Clientes, Fornecedores, Documentos, Stock, Imobilizado, Fiscalidade, Relatórios, Fecho, Auditoria e Definições.

`Home.tsx` mantém um `moduleData` com várias linhas demonstrativas antigas. A construção de `displayRows` usa consultas reais em vários módulos, mas também usa `data.rows` como fallback quando o resultado está indefinido. Isto pode mostrar dados de demonstração durante loading, indisponibilidade de uma query ou num módulo sem contrato real, contrariando o requisito de dados honestos. É uma lacuna crítica de confiança, mesmo quando a query persistente existe.

O módulo Empresas contém fallback demonstrativo explícito no `moduleData`, embora o carregamento operacional use `companies.list`. O Overview já filtra visualmente o tenant descartável e mostra Repair Lubatec, mas a lista persistente continua a conter o registo descartável para testes.

As rotas de navegação e os títulos dos módulos estão centralizados no `DashboardLayout`/`Home`. A matriz backend precisa de ser cruzada com cada superfície: leitura, criação, actualização, emissão/posting, exportação, auditoria, permissões e estados de loading/erro.

## Evidências backend e de fluxo

A árvore tRPC tem contratos persistentes para empresas, contrapartes, catálogo, tesouraria, AGT/preparação, contabilidade, fiscalidade, documentos, exportação/importação, ficheiros, reversões, moeda, fecho, imobilizado, inventário, reconciliação, relatórios e auditoria. Isto demonstra uma base backend ampla, mas não prova que todas as acções estejam expostas e utilizáveis na UI.

A matriz RBAC é simples e explícita. Admin tem acesso total; Contabilista tem contabilidade, documentos, fiscal, stock e fecho; Financeiro concentra-se em tesouraria e dados comerciais; Operador não tem emissão, posting, fecho ou fiscalidade; Auditor é predominantemente leitura e auditoria. Deve ser verificado que a UI esconde/desactiva acções incompatíveis, em vez de apenas deixar a API rejeitar.

Lacunas backend concretas: `getSaftReadinessForUserCompany` envia `customerCount`, `supplierCount`, `productCount` e `taxRuleCount` como zero, apesar de existirem tabelas/queries desses domínios. Isto torna a prontidão SAF-T incompleta e pode bloquear ou falsear o diagnóstico. `reports.saftExport` bloqueia deliberadamente com `SAFT_EXTERNAL_VALIDATION_REQUIRED` quando a prontidão passa, portanto não há exportação SAF-T final disponível sem uma etapa de validação externa.

A UI expõe criação real para contrapartes, catálogo, contas de tesouraria, activos fixos, movimentos de stock, séries e rascunhos de documentos. Porém, a grelha principal é uma representação genérica; várias operações backend existentes — lançamento contabilístico, reversão, reconciliação bancária, depreciação, exportação SAF-T, submissões AGT, períodos e exercícios — não têm, nesta superfície, um formulário operacional completo ou uma página dedicada.

A importação/exportação tem validação, revisão e privacidade, mas a confirmação de documentos importados permanece bloqueada por desenho (`FISCAL_DOCUMENT_IMPORT_REQUIRES_REVIEW`); o fluxo de revisão existe, mas precisa de aceitação manual com ficheiro real anonimizado. O PDF é explicitamente de preparação, não certificado.

Os testes são fortes em regras, routers, isolamento, fiscalidade e happy paths backend, mas os testes de Home usam hooks tRPC simulados. Assim, comprovam ligação visual e mensagens, não a persistência real de cada clique no browser. Falta uma camada de testes de aceitação autenticados para os principais fluxos de utilizador.
